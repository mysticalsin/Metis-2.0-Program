## 2. Principles

| Principle | What it means here |
|---|---|
| **Simplify** | Few owned mechanisms inside the existing app (supervisor, storage gateway, reveal controller, journal, scheduler) instead of new services; no rewrite, no framework switch, no DI container, no desktop database. Every new runtime component passes the admission contract (ARCHITECTURE §2.7). |
| **Evidence over narrative** | A ticket closes only with one evidence record per required level; packaged claims cite the lane sha256; prose never counts. The biggest program risk is false closure. |
| **Tests first** | A bug fix starts with a test that fails on the parent commit and passes after (red-before/green-after, both recorded). Acceptance is written before implementation. |
| **Hermetic tests** | No agent runs any repository test until M2-0001's canary passes, and then only in CI (honeypot), on the isolated QA macOS user, or on the owner's account under the OS sandbox profile once D-28 is applied. |
| **No fakes** | No mock metrics, stub endpoints, guessed model IDs, placeholder receipts or success templates in production paths. Contract fakes live only in tests. "Wired for real" = real client path + schema-faithful contract fake in tests + one-command live probe + BLOCKED in the capability matrix. |
| **Kill-safe first** | Any process may die at any moment: sidecars die with it, acknowledged edits survive, the next boot is calm. |
| **Honest readiness** | Engineering-complete and real-environment BLOCKED are different statuses; an owner or vendor action is never faked. |

## 4. Methods and how they apply to each ticket

**software-architecture-engineer v1.4.0.** Each ticket runs in one mode: `investigation` tickets in **AUDIT**; new components (supervisor, gateway, journal, index, sampler, lane) in **DESIGN** with a component admission record (requirement, simpler alternative and why it fails, owner, failure behaviour, exit path); fixes and refactors in **EVOLVE/IMPLEMENT** as reversible slices. Every claim in a ticket, PR or evidence record carries an evidence label. Gates issue a scoped readiness verdict: DESIGN_READY, DESIGN_BLOCKED, IMPLEMENTED_NOT_VALIDATED, VALIDATED_IN_SCOPE or RELEASE_BLOCKED.

**Stark v9.3.0.** The ledger is the numbered ticket system. PRD before MVP: the one-page policy approval (M2-0189) and the full PRD lock (M2-0016); acceptance lines exist before implementation. Tests first. The validator runs the structured five-axis review on the actual diff and evidence. A numbered lesson is recorded after each accepted slice (`docs/metis-2.0/lessons/`), and `_relay/HANDOFF.md` is the baton between sessions. Evidence levels are distinct: each ticket lists the set it needs in `required_evidence`.

**Per ticket, in order:** read the ticket and its artifact dependencies → confirm the decision defaults it relies on (`needs_decision`, labelled ASSUMED) → write the failing test or the design state list → implement the slice → run targeted checks under the hermetic harness → write the evidence record → open the PR with the template → Opus validator review → orchestrator merges through the queue → lesson and baton update.

## 5. Architecture summary

Full design: [ARCHITECTURE.md](ARCHITECTURE.md). Métis stays one Electron app, reshaped into a modular monolith (`main/{app,lifecycle,windows,ipc,features,infra}`, `renderer/{app,features,ui}`, `shared/contracts`) through strangler steps guarded by fitness functions FF-01..FF-16. The owner's bugs come from one loop (DERIVED: the spindumps OBSERVED the main thread blocked in synchronous reads of dataless files and the orphans are CONFIRMED; the chain between them is inference): synchronous reads of dataless OneDrive files stall the main thread → the user force-quits → `llama-server` sidecars (about 3.1 GB each) are orphaned → relaunch triggers background work that cold-starts the local model again; separately, reopen is a no-op while the overlay is parked in Hide. The loop is broken by:

- **C1 supervisor:** one `stopAll()`, identity-safe registry and reaper, `mac-helper supervise` (HK-M 20/20 to default on).
- **C4 storage gateway:** async only, one global in-flight cap ≤ pool − 2, dataless detection before any read, degraded results instead of waiting.
- **C2 reveal controller:** one `reveal()` for every reopen path; journal-gated renderer recovery from m6.
- **C6 scheduler:** one retry/exhaustion policy, a 120 s boot quiet period, and suspension while the ledger is unavailable.
- **C3 journal, C5 index and ledger:** acknowledged edits survive SIGKILL; History renders from a local index; the ledger moves out of the synced folder.
- **C9 observability and C15 stall sampler:** every hypothesis is discriminated on packaged builds.

The 2.0 intelligence features (Jev/Laya, Hindsight memory, the governed knowledge API, Teams) live server-side behind Operator and Entra; the desktop stays a key-less client. Verification is part of the architecture (ARCHITECTURE §7): isolated environments, a build-once candidate lane, owner-channel trains and a feature freeze.

## 8. The release evidence chain

One immutable record per ticket per required level (M2-0002): requirement or defect → reproduction → commit → artifact sha256 → environment and host identity → command and exit code → result → implementer session → validator session → per-kit-reference status (MET, PARTIAL, BLOCKED, NOT_MET).

| Level | What a record must contain |
|---|---|
| DESIGNED | The design artifact (spec, prototype, decision) and the validator's acceptance |
| LOCALLY_TESTED | A CI run ID on the PR head SHA; for fixes, red-before on the parent commit and green-after |
| HOST_CONFIGURED | The configured host or service, the probe output and who authorized it |
| LIVE_VERIFIED | Harness-produced suite or census output on a packaged artifact identified by its lane sha256, plus host identity; never prose, never a dev build |
| ACCEPTED | The owner's dated statement |
| MEASURED | The raw measurement file, the accounting boundary and the environment |

**Dependency semantics.** `depends_on` lists artifact dependencies: a ticket enters the ready queue when each is ENGINEERING_COMPLETE, DONE, DEFERRED or BLOCKED_EXTERNAL; while one is BLOCKED_EXTERNAL the ticket can close only as ENGINEERING_COMPLETE, its records carry `inherited_block`, and it becomes DONE when the upstream is DONE and the affected verification is re-run. `needs_decision` lists D-x decisions: work proceeds on the recorded default labelled ASSUMED, is never capped, and is re-validated if the answer differs. The program sign-off may be DONE with inherited blocks listed (the goal's definition of done).

**Release path.** Candidate built once by `qa-candidate.yml` → packaged gates on those bytes (QA user, Windows lanes) → evidence records → Opus validation → owner approval → `promote-candidate.yml` publishes the same bytes (owner channel under D-13) → release branch cut. Versions: 1.9.7 → 1.9.9 → 2.0.0-beta.1 → 2.0.0-beta.2 → 2.0.0-rc.N → 2.0.0; 1.9.8 is never reused. `scripts/release/decide.mjs` (M2-0171) computes the MASTER section 27 release decision on the release commit.

## 10. Branching, pull requests and merges

The repository is private on a plan tier where branch protection cannot be enabled (the API returns HTTP 403), so nothing at GitHub level blocks a bad merge. Enforcement therefore sits in CI, the PR template and the merge queue:

- **Branches:** `m2/M2-####-slug` from `main`, one ticket or one slice per branch, in an isolated worktree; `fix/<slug>` for hotfixes; `release/1.9.x` cut at the 1.9.7 tag. PR base is always `main` (no stacked PRs), except backports to `release/1.9.x`.
- **Commits:** conventional commits with the ticket id, for example `fix(recall): route list through the gateway [M2-0193]`.
- **Pull requests:** `.github/pull_request_template.md` (extended by M2-0002) requires the ticket, kit references, findings, the evidence record path, the evidence levels reached, what was not run and why, and the reviewing model. PRs are either **pure move** (checked by `verify-move.mjs`) or **behaviour change**, never both. A PR stays in draft until the Opus validator (a different session) records its review.
- **Merges:** only the Opus orchestrator merges, in queue order, after green CI and a passing `scripts/evidence/check.mjs`. Hot files (`src/main/index.ts`, `App.tsx`, `shared/ipc.ts`, the preload, `package.json` and the lockfile, the workflows, `mac-helper/main.swift`, the ledger) land one at a time; `claims-check.mjs` rejects overlapping claims and more than three concurrent `src/main` agents.
- **Backports:** fix on `main` first and cherry-pick to `release/1.9.x` with the same test; where code has moved, write the 1.9.x fix against the release branch and link both.
- **Tags and releases:** agents never push tags. The promote workflow creates tags and owner-channel prereleases from tested bytes after the owner approves. `release.yml` is not used for 1.9.x or the trains.
- **Secrets and content:** gitleaks scans `docs/**.md`; no secrets, account IDs, personal emails or meeting content in code, docs, commits, `_relay/` or PR text.
