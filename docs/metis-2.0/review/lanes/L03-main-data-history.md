## 0. Executive summary — the one finding that matters most

I found a live, currently-active, well-evidenced causal chain that plausibly explains **both** of Tony's bug reports at once ("heavy on my PC" and "History sometimes doesn't open — running but frozen/crashed"):

1. **OBSERVED** on Tony's real, currently-live meetings folder (`~/Library/CloudStorage/OneDrive-MantuGroup/Métis Meetings/.brain/`): **178** `index.corrupt-<ISO timestamp>.json` quarantine snapshots, dated 2026-08-20 through 2026-09-23, with a sharp acceleration in the final week (15 on 09-19, 48 on 09-20, 25 on 09-21, **64 on 09-23** — the day before this audit's runtime evidence was captured). 2. **OBSERVED** in code: `quarantineUnusableIndex()` (`src/main/brain/store.ts:447-469`) is the *only* code path that produces an `index.corrupt-*.json` file. It fires whenever `readIndex()` (`store.ts:471-477`) finds `.brain/index.json` present but unparseable/undecryptable, and it **renames the bad file away and starts the brain index over from empty** — by design, on purpose, and it never deletes the quarantined copies (same policy is documented for `corrections.corrupt-*.json` in `corrections.ts:365,423`).
3. **OBSERVED** in code: every place that decides "what still needs ingesting" — `startBackfill()` (`brain/ingest.ts:2531-2618`, esp. line 2542 `already = new Set(...idx.ingested...)`) and `reconcileMeetingsInBackground()` (`brain/ingest.ts:2798-2817`, wired to fire once at boot and then every 60s forever via `index.ts:9347,9367,9373`) — reads that same `index.json`. When it comes back empty (post-quarantine), **every already-processed meeting looks unprocessed again**, and the app requeues the whole vault (56 of Tony's 57 real meetings already have a cached extraction in `.brain/meetings/`, so most of this requeue is a "reconcile" merge rather than a fresh LLM call — but at least one/some do not, which lines up with the lead's runtime evidence E4: a burst of ~20 `brain.ingest` events within 200ms, a 30-41s cold local-LLM call, and some `brain.ingest ok:false`, on every observed app start).
4. This reconcile-storm is genuine, repeated, avoidable CPU/disk/LLM work happening far more often than the design intends (twice-daily "named slots" per `consolidate.ts`'s own doc comment, not per-boot-and-every-60s), and it is **triggered by the very same instability** (repeated force-quit/crash, E2/E3/E6/E9) that a corrupted index also degrades — i.e. this is very plausibly a **feedback loop**, not two independent bugs.

What I could **not** pin down from this lane alone: the exact mechanical trigger of the corruption/undecryptable event itself. I verified the write path (`writeSaved`, `transcripts.ts:342-378`) *is* properly atomic (unique per-call tmp name, `rename()`, bounded EPERM/EBUSY retry) — a crash mid-write should leave the **old** `index.json` intact, not a corrupt one, so a naive "torn write" explanation doesn't fully fit the evidence (see §3.1 for the reasoning and the two remaining candidate mechanisms). This needs one more turn of investigation (correlating `index.corrupt-*` timestamps against `audit.log`'s crash timestamps, which I did not have permission/reason to open in full — see §5 gaps) before a fix is designed, but the **symptom, its scale, its trigger-side code, and its consequence-side code are all now nailed down with file:line citations**, which should make that next step fast for whoever owns E2/E3/E6/E9.

A secondary, independently-confirmed real incident: `settings.json.recovered` exists in `userData`, dated **2026-07-18**, 378 bytes — proof that Tony's `settings.json` (which holds `meetingsFolder`, context docs, MCP connections, etc.) genuinely went unreadable once, in the past, and the app silently fell back to defaults with only a `mainLog.warn` (see §4).

Breakdown: 59 `.md` (57 real meetings + `index.md` + `README.md`), 283 `.json` under `.brain/`, 18 stray `.tmp` under `.brain/`. `.brain/` itself is 520K; a `.brain.backup-v1/` safety-copy directory (0B — OneDrive dataless placeholders) sits beside it from the v1→v2 entity migration (`store.ts:352-421`).
- **Two other "meetings folder" locations exist on Tony's disk** (data-fragmentation risk, see finding L03-11): a legacy `OneDrive-MantuGroup/AskToto Meetings` (361 files, 0B — OneDrive online-only placeholders; the one-time copy-forward marker at `userData/.copied-legacy-asktoto-meetings` shows it already ran, 2026-08-07) and an orphaned `~/Documents/Métis Meetings` containing only the two auto-generated bookkeeping files (`index.md`, `README.md`, no real meetings) — evidence that `ensureMeetingsFolder()`/`resolveMeetingsFolder()` created a *second* root at some earlier point when OneDrive detection resolved differently.
- **`.brain/` is the "brain" — a plain-JSON-files-on-disk knowledge store** (`brain/store.ts:25-36`), deliberately co-located with the transcripts so it inherits OneDrive sync and the same at-rest encryption. Sub-paths: `index.json` (the ingest ledger + revision counter — `BrainIndexSchema`), `graph.json`, `meetings/<slug>.json` (per-meeting cached extraction), `entities/{person,account,deal}/<slug>.json`, `consolidate-state.json`, `corrections.json` (human-correction journal).
- **Encryption**: transcripts, notes, and every brain JSON file share one envelope format (`ATKENC2` = AES-256-GCM content key wrapped via OS keychain (`safeStorage`) +/− an org-escrow public key; legacy `ATKENC1` = direct `safeStorage`). **`settings.json` itself is encrypted at rest with the same scheme** (confirmed on Tony's real `settings.json`: file starts with the `ATKENC2\n` magic bytes) — i.e. app configuration (which may hold nothing sensitive, like `meetingsFolder`) pays the same keychain-bound decrypt cost and the same "undecryptable if the keychain/signing identity changes" fragility as transcript content (`store.ts:332-499`, esp. the format-cascade in `tryParseSettingsBuffer`, `store.ts:355-378`).

### 1.2 Data flow for "History" / Recall
- `listMeetings()` (`recall.ts:237-244`) and `searchMeetings()` (`recall.ts:949-978`) are the two functions that build the History/Recall surfaces (their only callers are IPC handlers in `index.ts`, outside this lane). Both list the meetings folder (`meetingFiles()`, `recall.ts:58-67`, async `readdir`), then `Promise.all(...map(readMeeting))` over **every** file to get a `{sum, text}` pair.
- `readMeeting()` (`recall.ts:139-165`) is genuinely well engineered: a per-file cache keyed by `(mtimeMs, size)` (`recall.ts:124-135`), a distinct `UNREADABLE` sentinel (transient failure, never cached) vs. `null` (permanently "not a meeting", safe to cache), and a `LockedMeetingSummary` stub (`recall.ts:81-115`) so an undecryptable-on-this-device meeting still shows up in History instead of silently vanishing. This is one of the better-designed corners of the codebase.
- **Brain index** (`.brain/index.json`) is the single source of truth for "has this meeting file been ingested into the knowledge graph" (`ingested[file] = {ok, at, sourceVersion, attempts, retryAfter, exhausted}`). All mutation goes through one serialized lane, `updateIndex()` (`brain/ingest.ts:1341-1352`) — this *is* correctly locked (see §3.1); entity files (`person`/`account`/`deal`/`graph`) share a second lane, `withEntityLock()` (`brain/store.ts:279-289`).

### 1.3 What's genuinely good here
This lane is **not** sloppy code. It shows real production hardening, with dozens of inline comments citing specific prior review fixes (`MQA-023`, `MQA-105`, `MQA-175`, `MQA-230`, `MI-2`, `MI-2.5`, `MI-4`, `MI-5`, `MQA-309`...) — meaning this exact area has already been audited and iterated on multiple times before this v2.0 pass. Specific examples worth preserving, not rewriting:
- Atomic writes everywhere (`writeSaved`, `transcripts.ts:342-378`): unique per-call tmp name (avoids two writers racing on one `${file}.tmp`), bounded retry on Windows/OneDrive `EPERM`/`EBUSY`, tmp cleanup on failure.
- `quarantineUnusableIndex`/`corrections.ts`'s equivalent: **never destroy** a file that might be recoverable — rename aside, log, degrade gracefully. Correct instinct; the bug is that its trigger fires far more than intended, not that the mechanism itself is wrong (see the finding below).
- Two independent serialization lanes (`indexLock`/`updateIndex` for `index.json`, `withEntityLock` for entity files) with an explicit inline comment (`ingest.ts:1333-1340`) describing the exact production bug this fixed (concurrent read-modify-write on `index.json` silently dropping writes) — a real regression test in prose, not just a fix.
- `settings.json`'s three-format decode cascade with a `.recovered` last-resort backup that is itself tried *before* being overwritten (`store.ts:406-499`) — careful, fail-closed, well thought through.

## 2. Findings (ranked)

### L03-01 — P1 (reliability/architecture) — Brain index corruption is firing at high, accelerating, currently-active frequency, and the fallback ("rebuild everything") makes the underlying instability worse
- **File**: `src/main/brain/store.ts:447-477` (`quarantineUnusableIndex`, `readIndex`); trigger side `src/main/brain/ingest.ts:2531-2618` (`startBackfill`), `2798-2817` (`reconcileMeetingsInBackground`); scheduling `src/main/index.ts:9347,9367,9373`.
- **Evidence** (OBSERVED, real disk): 178 `index.corrupt-*.json` files in `.brain/`, spanning 2026-08-20→2026-09-23, with counts by date: 4 (08-20), 1 (08-24), 8 (09-06), 1 (09-07), 3 (09-10), 3 (09-12), 3 (09-15), 1 (09-16), 15 (09-19), **48 (09-20)**, 25 (09-21), 2 (09-22), **64 (09-23)**. Most are 474 bytes (a near-empty index — i.e. the rebuilt index is *also* getting quarantined almost immediately, repeatedly, in the same window); a minority are 12-20KB (closer to the live index's current 13,898 bytes), meaning genuine "fuller" indexes have also been lost at various points.
- **Failure scenario**: On any read where `readSavedFile()` → `JSON.parse()` throws or `BrainIndexSchema.parse()` throws, `readIndex()` (`store.ts:471-477`) treats the index as absent, quarantines the bad bytes, and returns a **fresh empty index**. The very next `startBackfill()`/`reconcileMeetingsInBackground()` call (boot, or the 60s timer, `index.ts:9347/9373`) sees `idx.ingested = {}` (`ingest.ts:2542`), so *every* real meeting file looks uningested, and gets requeued (`ingest.ts:2574-2618`). Most requeues take the cheap "reconcile" path (56 of Tony's 57 meetings already have a `.brain/meetings/*.json` extraction cached, so `strategy: 'reconcile'` at `ingest.ts:2602` avoids a fresh LLM call) — but this still means a full sequential re-merge of every person/account/deal entity, under `withEntityLock`, on every corruption event, plus at least one genuine fresh extraction (matching the lead's E4: a 30-41s local-LLM cold start and some `ok:false` results) when a meeting's cache is also missing or stale.
- **Why this matters for Tony's two complaints**: "Heavy on my PC" — a reconcile-storm of up to dozens of meetings plus a cold local-LLM spin-up is real, repeated CPU/RAM/disk work that the design (`consolidate.ts`'s own comment: "twice-daily... named 06:00/12:00/18:00 slots... not an hourly poll") did not intend to run this often. "History sometimes doesn't open" — while I did not find synchronous main-thread blocking *inside* the reconcile path itself (extraction and merge are async/off-thread where I checked), a process that is mid-reconcile-storm, combined with the crash pattern in E2/E3/E6/E9, is consistent with the renderer appearing to hang while the main process is busy.
- **What I could not confirm** (§3.1 below): the *original* trigger for why `index.json` becomes unparseable/undecryptable this often. The write path is atomic by inspection, so this is not an obviously torn write.
- **Fix direction**: (a) instrument `quarantineUnusableIndex`'s existing log line (`store.ts:463-465`, which already says "unparseable" vs. "undecryptable (`reason`)") into a metric/counter so this stops being invisible — it currently only reaches `mainLog.warn`; (b) once the exact decode failure reason is visible in aggregate, decide the real fix (likely: don't let a keychain-transient failure be indistinguishable from real corruption — see §3.1's candidate #2); (c) separately, `hasIncompleteMeetingSource`/`hasMeetingSourceDrift`-style guards should recognize "index was *just* quarantined this boot" and back off the reconcile cadence instead of immediately re-triggering a full requeue, to break the feedback loop even before the root trigger is fixed.

### L03-02 — P2 (architecture/resource) — Quarantined corruption snapshots (and the equivalent for the correction journal) are never cleaned up, by explicit design, with no size/age cap
- **File**: `src/main/brain/store.ts:447-469`; identical pattern for corrections at `src/main/brain/corrections.ts:365,420-423` (`corrections.corrupt-*.json` / `corrections.corrupt-conflict-*.json`).
- **Evidence**: grep-confirmed (OBSERVED) — no code anywhere in this lane (or the wider repo, checked via `index.ts`) ever deletes a `*.corrupt-*.json` file. The design intent is explicit and reasonable in isolation ("quarantine, log it, never delete" — `store.ts:435-436`), but nobody anticipated the trigger firing 178 times in five weeks. This directory syncs to OneDrive and, per `brain/store.ts:28`, is deliberately readable by Dust agents as vault context — 178+ near-duplicate stub files is real sync bandwidth, real directory clutter, and a real risk of confusing any other consumer that globs `.brain/*.json` without excluding the `.corrupt-` infix (most in-lane readers do filter correctly, e.g. `corrections.ts:222`, but this is now a convention every future reader must remember).
- **Fix direction**: cap total quarantine bytes/count per brain dir (e.g. keep the newest N, or roll up to a single "last N corruption events" ledger instead of one full-index-sized file per event), or at minimum surface a "brain has accumulated N corruption snapshots — consider running a repair" affordance instead of silent unbounded accumulation.

### L03-03 — P1 (performance/reliability) — Resumable-import checkpoint loading is fully synchronous, unbounded, and runs on the main thread at boot
- **File**: `src/main/import-job-store.ts:24-49` (`EncryptedImportJobStore.list()` — `readdirSync`, `statSync`, `readSavedFile` per file, all sync), called from `src/main/import-jobs.ts:299-336` (`ImportJobManager.recover()`, called once per app start).
- **Failure scenario**: Every checkpoint file under `userData/import-jobs/` holds a job's full `lines: []` array (transcript lines accumulated so far for a long, interrupted import — `import-jobs.ts` comments confirm these are resumable long-recording imports). Given the app's own crash/force-quit pattern (E2/E3/E6/E9), it is entirely plausible for several import jobs to sit in a non-terminal state at any given time. `recover()` awaits `store.list()`, but `list()`'s actual disk work — directory enumeration, N `statSync` calls, N full synchronous reads+decrypts+`JSON.parse`s — all runs synchronously back-to-back with no yield to the event loop, contradicting the async-everywhere discipline the rest of this lane follows (contrast with `recall.ts`'s async `readMeeting`/`readCache`, or `writeSaved`'s async write).
- **Fix direction**: switch `list()` to `fs/promises` (`readdir`, `stat`, and an async decode) exactly as `recall.ts` already does for meeting files, so a boot with several/large pending imports doesn't block the main process.

### L03-04 — P2 (performance/architecture) — `listMeetings()`/`searchMeetings()` fan out an uncapped `Promise.all` across every file in a cloud-synced folder
- **File**: `src/main/recall.ts:237-244` (`listMeetings`), `949-978` (`searchMeetings`).
- **Evidence**: both call `Promise.all((await meetingFiles(folder)).map((f) => readMeeting(folder, f)))` with no concurrency cap. Contrast with `src/main/brain/ingest.ts:1259`, `const EXTRACT_CONCURRENCY = 3`, whose own comment explains exactly why unbounded parallel LLM extraction was a problem — the same reasoning applies here to unbounded parallel file I/O against an OneDrive Files-On-Demand folder (a placeholder read can trigger network hydration).
- **Scale today**: fine — 57 files, 892KB. **Will not scale**: every `listMeetings()`/every keystroke of a search box (subject to whatever debounce the renderer applies, out of lane) re-touches every file's `stat()` even when cache hits avoid the full read.
- **Fix direction**: a small concurrency limiter (the same pattern already exists in this file's sibling `ingest.ts`) around the `map`, or paginate/limit History to a recent window with search falling back to the index rather than raw files.

### L03-05 — P2 (performance) — `entityDirStamp()` is a documented per-answer "hot path" N+1 sync-`statSync` pattern
- **File**: `src/main/brain/match-key-cache.ts:22-48`, doc comment at lines 6-7: "Hot path on every answer ask: one directory `statSync`..." — but `entityDirStamp()` (used for Receipt Mode's cache-validity check) does one `readdirSync` **plus one `statSync` per `.json` file** in the entity directory (lines 35-42), not just the single directory stat the module comment implies.
- **Failure scenario**: currently small (a few dozen entity files), so low absolute cost — but this is exactly the N+1 pattern the audit brief called out, on a path explicitly documented as hot, and it will degrade linearly as Tony's person/account/deal entity count grows.
- **Fix direction**: use the directory's own `mtimeMs` + `readdirSync().length` as the cache-validity stamp (which is what `count` already captures) and drop the per-file `sizeSum` stat loop, or maintain a running byte-total incrementally on write instead of re-summing on every read.

### L03-06 — P2 (performance) — Sync `readdirSync`-based checks run forever on a 60-second main-process timer, not just at boot

## 3. Supporting reasoning

### 3.1 Why the write path doesn't obviously explain the corruption (and what to check next)
`writeSaved()` (`transcripts.ts:342-378`) writes to a uniquely-named temp file, then `rename()`s it over the target, retrying on `EPERM`/`EBUSY`. A `rename()` within the same filesystem/volume is atomic at the OS level, so a process killed *before* the rename leaves the **old** file untouched, and a process killed *after* the rename has already committed the new content — there should be no window that leaves `index.json` holding half-written bytes. Two candidate mechanisms I could not rule in or out from static code alone, both worth a real log-correlation pass before designing a fix:
1. **Keychain/`safeStorage` transient unavailability right after a crash-relaunch.** `quarantineUnusableIndex`'s own log line distinguishes "unparseable" (JSON syntax) from "undecryptable (`reason`)" (`store.ts:463-465`) — if the real cause is mostly the latter, a perfectly intact, correctly-written `index.json` is being wrongly treated as corrupt because the OS keychain (or the file-backend content key) is momentarily unreachable during/just-after a crash-storm boot, and the fix is "distinguish transient-undecryptable from permanently-undecryptable" rather than anything about the write path.
2. **OneDrive Files-On-Demand interaction on macOS.** The folder is OneDrive-synced; a `rename()` target that OneDrive's File Provider extension is mid-hydrating/mid-uploading is a known source of surprising read behavior on macOS (distinct from the Windows-specific `EPERM`/`EBUSY` case `writeSaved` already retries around). I did not have a way to test this directly without violating read-only/content-read constraints.
- **What would resolve this in one pass**: grep `mainLog`/`audit.log` for the exact strings `quarantineUnusableIndex` logs ("was unparseable" vs. "undecryptable (...)") and correlate their timestamps against the crash/force-quit timestamps the lead already collected (E3, E6). I did not do this myself — my brief scoped runtime-log correlation to the lead's already-collected E1-E9 evidence, and opening `audit.log`/`mainLog` further was not clearly authorized as "my lane's files."
