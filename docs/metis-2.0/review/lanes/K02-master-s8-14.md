### 7.3 Code correlation: REQ-S14-04 (signed manifest + trust chain) — integrity present, cryptographic signing/trust-root absent

**OBSERVED.** `asr-model-manifest.ts`'s own header comment is unusually candid and directly relevant: it explains the manifest pins a 40-hex immutable Git commit (never `main`, enforced by `asr-model-manifest.test.ts`) specifically because `/resolve/main/` is a mutable ref that "two builds a month apart can... embed different bytes under the same version, and nothing would notice" — and every file carries a `sha256` that is "the LFS oid reported by the Hugging Face API for this exact commit — upstream's own digest, not one computed from a local copy that could itself have been wrong." This is genuine, well-reasoned **integrity** engineering (content-addressing + immutable-revision pinning) and partially satisfies REQ-S14-04's "pin immutable content-addressed assets" clause. **What it does not satisfy**: REQ-S14-04 requires a *signed* manifest with an *executable signer* identity and a trust root that lives in the signed application or an authenticated root-update chain, explicitly warning that "a checksum fetched from the same compromised location is not an independent trust root." The SHA-256 values here are fetched from the Hugging Face API at build/pin time — the same third party serving the files — which is precisely the "checksum from the same location" pattern the spec calls out as insufficient for a genuine trust root, not because the engineering is careless (it manifestly is not) but because integrity-via-vendor-reported-digest and cryptographic-signature-with-an-independent-trust-root are two different guarantees, and only the first is present here. I record this as a **P2 gap** (real, structural, but not an active exploit given Hugging Face's own TLS+auth model) rather than P0/P1.
