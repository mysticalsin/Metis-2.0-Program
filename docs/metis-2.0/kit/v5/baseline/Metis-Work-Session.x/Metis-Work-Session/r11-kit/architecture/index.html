SRC-01 · INPUT LIMITATION

Do not mistake a source export for a complete checkout

The export contains 1,521 FILE sections and package version 1.9.5. Five of the 19 file-backed nodes in the supplied map have no source section: renderer App.tsx, main index.ts, renderer lib/listen.ts, main/transcripts.ts and main/brain/ingest.ts. Imports and tests mention them; that does not recover their contents. The filename suffix is not an established Git commit.

Implementation and proof

Acquire the authorized real checkout and its commit/dirty state. Compare source hashes before using anchors. Preserve the export as historical evidence; never generate stub replacements or run an incomplete reconstructed app as the baseline.

Acceptance: Exact checkout/branch identity and a missing-versus-present source manifest; baseline checks on the complete tree, with every skipped suite explained.

SRC-02 · ARCHITECTURE GAP

Separate entitlement authority from telemetry and legacy licensing

The map separates a license service but omits the consumer edges. Operator has issued-license/seat records, while the legacy service has a serialized JSON store and a separately configured offline lease key. The legacy module describes compiled-off UI gates; the corresponding current renderer files are absent, so actual gate enablement is not established.

Implementation and proof

Choose one issuer/entitlement authority for each active distribution profile. Entra authenticates identity; a signed license or lease grants only its exact entitlement; telemetry supplies neither identity proof nor permission. Reconcile legacy and Operator IDs without switching on conflicting gates. Production rejects development trust roots. Preserve recovery/export access when paid inference is unavailable.

Acceptance: Activation, renewal, revoke, expired/clock-skewed lease, duplicated device, reinstall, entitlement loss, two-user isolation and cross-process seat-cap races on the actual chosen store. JSON mutex cannot be represented as a distributed lock.

SRC-04 · SOURCE DEFECT

Execution result and exception handling must control completion

flushPending awaits executeDesktopAction but ignores the returned ok/outcome before mark_committed. A test on unsupported Linux expects a committed action; this proves bookkeeping, not successful desktop control. A rejected execution can also re-enter flushPending from finally while pending remains.

Implementation and proof

Separate dispatch acceptance, attempted side effect, verified completion and unknown outcome. Consume every result and caught exception. Quarantine an uncertain non-idempotent attempt until reconciliation. Retry only bounded classified safe failures; stop must prevent further dispatch.

Acceptance: Adapters returning failed, unsupported, unknown, cancelled or throwing never produce verified success. A rejected or timed-out write cannot create an unbounded retry loop or duplicate note.
