**Image signing.** The pinned API image index carries a cosign signature tag (`GET ghcr.io/v2/vectorize-io/hindsight-api/manifests/sha256-35a1c04c3b50172707d627f82d7f7800d7695b8d9e630142354e3365e5ce56ba.sig` returns `200`). Its manifest has 5 layers — not one certificate per signed sub-manifest of the index, as an earlier draft of this pin claimed. All five layers are in fact the *same* `application/vnd.dev.cosign.simplesigning.v1+json` payload blob, digest `sha256:cc993191512bf25548e6f86b4639fc5b5214f3b64f6e349dea9c10b9645e846e`, whose `critical.image.docker-manifest-digest` is the image-index digest itself (`sha256:35a1c04c3b50172707d627f82d7f7800d7695b8d9e630142354e3365e5ce56ba`). The five layers carry five distinct signatures over that one payload, each with its own Rekor entry (`integratedTime` 1790003481–1790003500, five entries logged 19 seconds apart in total) — i.e. a single `cosign sign` invocation that signed multiple tag refs at once, per `.github/workflows/release.yml`'s "Sign published images" step (`release.yml:499-510`, which loops over `TAGS` and runs one `cosign sign --yes "${refs[@]}"`; :496-497 only installs cosign, and :512-519 is upstream's own — regexp-based — verify step, not evidence for this pin), using keyless signing — not `sign-images.yml`, which does not sign this image. All five layers carry one and the same Fulcio certificate (serial `5ED9667B7B948C3452968B6EEE1621AB6FBE2C43`), whose Subject Alternative Name (read at §2) is `https://github.com/vectorize-io/hindsight/.github/workflows/release.yml@refs/tags/v0.10.1`, whose OIDC-issuer extension is `https://token.actions.githubusercontent.com`, and whose workflow-SHA extension is `f8950b0c07d9e34c76493dba802bb309f0ce60fd` — the pinned release commit.

The per-arch child manifests carry no signature of their own: `GET .../manifests/sha256-7e7378b003fcac108d32111c3d75a5995a6fc7bfbd4f2a9047d68200ab364b01.sig` (`linux/amd64`) and `.../sha256-b53b8b017ab2770d353dd965976eab0757cd5414738c1d391eac84eabd0db719.sig` (`linux/arm64`) both return `404`. **Operational consequence:** verification must target the image-index digest, not a platform-resolved child digest. A deployment step that pulls a specific-architecture image (as Docker/containerd do once they resolve the index for the local platform) and records only that resolved child digest has recorded a digest with no signature to verify — the signature exists solely on the multi-arch index. An integrator can check provenance beyond tag-to-digest trust with the exact pinned identity, not a regexp:
```
cosign verify \
  --certificate-identity 'https://github.com/vectorize-io/hindsight/.github/workflows/release.yml@refs/tags/v0.10.1' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  --certificate-github-workflow-sha f8950b0c07d9e34c76493dba802bb309f0ce60fd \
  ghcr.io/vectorize-io/hindsight-api@sha256:35a1c04c3b50172707d627f82d7f7800d7695b8d9e630142354e3365e5ce56ba
```
`cosign verify` itself was not run against the live registry — a separate check from the certificate/digest/manifest reads this pin performs (§2); recorded so Métis's actual deployment step can run it. This strengthens HMSTEP-01's security clause beyond a bare tag-to-digest pin.

**Image-to-commit link.** Both `hindsight-api:0.10.1` and `hindsight-control-plane:0.10.1` carry the OCI config-blob annotations `org.opencontainers.image.revision=f8950b0c07d9e34c76493dba802bb309f0ce60fd` and `org.opencontainers.image.version=0.10.1`, read from the config blob referenced by each image's `linux/amd64` child manifest (`hindsight-api` config blob `sha256:2a21bc34854061c45571825cf5c6344d7c7ada1c80328cf423afb78ffca4fba0`; `hindsight-control-plane` config blob `sha256:90c781810befa363f8180df9c8476e4b6f1e7021d1f70f6dee4b7a879ee4c875`). This is what makes "the whole stack provably self-consistent" (below) a checked fact: the running container's own baked-in metadata names the release commit, and it matches the tag's dereferenced commit independently of the tag itself.

**Deviation from the prior source review, and why.** The r11-kit source review (`kit/r11/memory/SOURCE-REVIEW.md`, `kit/r11/memory/SOURCES.json`, reviewed 2026-09-23) recorded `upstream_ref: b88458fd6b96e70069238f7df5a0e2f1c3c9240c` — an arbitrary `main` snapshot, two days *newer* than the actual last cut release. This ticket pins to the tagged release (`v0.10.1` / `f8950b0c...`) instead, because (a) the acceptance criterion forbids `latest`/floating refs and a release tag is the only reproducible, versioned identity upstream publishes; (b) the npm and PyPI client packages, and the `openapi.json` `info.version`, all independently agree on `0.10.1`, so the whole stack (server, clients, schema) is provably self-consistent at this one commit, which is not true of an arbitrary main snapshot; (c) `b88458fd` remains reachable and is not stale (verified below), so nothing the r11 review cited is broken — it is simply not the identity to build against.

## 4. Delta note — STORE_DOCUMENT_TEXT, chunk/verbatim modes, tag-matching, replace semantics

**STORE_DOCUMENT_TEXT.** At the pin, `hindsight-api-slim/hindsight_api/config.py:1679`: `DEFAULT_STORE_DOCUMENT_TEXT = True  # Persist raw source text in documents.original_text / chunks.chunk_text`, and the versioned configuration doc is explicit: *"By default Hindsight keeps a verbatim copy of everything you retain... set `HINDSIGHT_API_STORE_DOCUMENT_TEXT=false`"* (`configuration.md:1914-1917`). **Métis must set `HINDSIGHT_API_STORE_DOCUMENT_TEXT=false` explicitly** (or the per-bank equivalent) wherever raw meeting/note text must not be persisted a second time outside the canonical store — the shipped default does the opposite. But this flag alone is not sufficient: see the next paragraph for the extraction modes it does not reach, and the paragraph after that for the fact that it is not even reliably a per-bank setting.

**Upstream self-contradicts on whether this is per-bank, and the code settles it.** `configuration.md:1719` (the `HINDSIGHT_API_STORE_DOCUMENT_TEXT` config-reference row) says it is "Hierarchical — overridable per bank via the config API." `configuration.md:1935` (the closing line of the STORE_DOCUMENT_TEXT prose section, `:1914-1935`) says the opposite: "This is a static, server-level setting and cannot be overridden per bank." The code resolves the contradiction in the hierarchical row's favor: `_CONFIGURABLE_FIELDS` in `hindsight-api-slim/hindsight_api/config.py` (~3653-3665) includes both `store_document_text` and `retain_extraction_mode` in the set of fields "that can be customized per-tenant/bank" — DERIVED: both are in fact per-bank, corroborated by `hindsight-api-slim/tests/test_store_document_text.py:44` ("``store_document_text`` is hierarchical (env → tenant → bank)") and the dedicated test at `:226-230` (`test_store_document_text_is_bank_configurable` asserts it is in `HindsightConfig.get_configurable_fields()`). Consequence for Métis: the server-level `GET /version` → `features.store_document_text` flag (which the kit client's `readiness()` check reads — `hindsight-client.mjs`) does **not** prove any given bank's effective value, since a bank's own config can override it either way; proving a bank's actual posture requires reading that bank's config via the bank config API, not the server-level `/version` response.

**Chunk/verbatim extraction modes store raw text as memories, and STORE_DOCUMENT_TEXT does not stop it.** `RETAIN_EXTRACTION_MODES = ("concise", "verbose", "custom", "verbatim", "chunks")` (`hindsight-api-slim/hindsight_api/config.py:1620`); default is `"concise"` (same file, line 1619). OBSERVED directly in the extraction code, not only inferred from docs: `hindsight-api-slim/hindsight_api/engine/retain/fact_extraction.py:3391-3392` returns `_extract_facts_chunks(contents, config)` for `chunks` mode before any LLM call is made ("chunks mode: skip LLM entirely, store each chunk as-is... Must come before the batch-API check so no LLM queue/locks are acquired"), and `:3497-3498` collapses extracted facts to the original chunk text for `verbatim` mode ("For verbatim mode, collapse to one fact per chunk with original text"). `fact_extraction.py` never reads `store_document_text` (no reference to it anywhere in the file) — confirming the config flag and the extraction-mode logic are independent code paths. In `verbatim` mode, "Each chunk is stored as a single memory unit with its original text preserved exactly — no summarization or rewriting" (`configuration.md:1963`); `chunks` mode stores chunks as-is with no LLM call at all (`developer/retain.md:296-297`, the extraction-mode table: "`verbatim` — When you need the original chunk text preserved..."; "`chunks` — When you want to store chunks as-is with no LLM call or extracted metadata"). In both modes, the memory unit itself **is** the original chunk text — `STORE_DOCUMENT_TEXT=false` only nulls the separate `documents.original_text`/`chunks.chunk_text` columns (`configuration.md:1920-1923`); it does not touch what gets extracted into memories. Worse, `"chunks"` mode is auto-forced when the main `llm_provider` (env `HINDSIGHT_API_LLM_PROVIDER`) is `"none"` (`hindsight-api-slim/hindsight_api/config.py:3963-3965`: `if self.llm_provider == "none":` sets `retain_extraction_mode = "chunks"`) — a no-LLM deployment silently switches to storing raw chunk text as memories, with no LLM extraction step to summarize it into facts, regardless of `STORE_DOCUMENT_TEXT`. This checks `llm_provider` specifically, not the separate `retain_llm_provider` override (which itself falls back to the resolved `memory_llm_provider` when unset — `hindsight-api-slim/hindsight_api/engine/memory_engine.py:2398`: `retain_provider = retain_llm_provider or config.retain_llm_provider or memory_llm_provider`, whose own fallback is derived at `:2250`: `memory_llm_provider = memory_llm_provider or config.llm_provider`) — the two must not be conflated when reasoning about which knob forces `chunks` mode. **Consequence: `HINDSIGHT_API_STORE_DOCUMENT_TEXT=false` alone does not guarantee "no raw text persisted"; a data-minimizing bank must also pin `retain_extraction_mode` to `concise`, `verbose`, or `custom`, and must not run with `llm_provider="none"`.** `api/retain.mdx:31,75` ("content is never stored verbatim... stores the resulting structured facts... not the original text") is therefore **false** under `verbatim`/`chunks` mode, and misleading even under the shipped default (`concise` + `STORE_DOCUMENT_TEXT=true`): the retain-extracted memories are indeed facts, but the separate document/chunk-text columns still hold the raw source a reader of only that guide would assume is never kept.

**Costs of disabling document text.** Per `configuration.md:1922-1933`: `update_mode="append"` is rejected outright (append must read back the prior text to extend it, and errors instead of silently dropping content); document export "carries no source text; re-importing such a bank cannot re-run extraction from the original payload"; the get-document, list-chunks, and get-chunk endpoints (and their MCP equivalents) return empty content; recall with `include_chunks=true` returns empty `chunk_text` (facts themselves are unaffected); reflect "no longer offers the `expand` tool... and its `recall` step stops attaching source chunks"; and reprocessing a document from its stored text becomes a no-op. Retain-pipeline quality (chunking → extraction → embedding → entity-linking) and recall itself are genuinely unaffected by disabling document text, but the six capabilities above (append, export, source reads, `include_chunks`, reflect expand, reprocess) are real, documented losses, not a null trade-off.

**Tag matching.** Five modes exist at the pin: `any` (default, includes untagged), `any_strict`, `all`, `all_strict`, and `exact` (`api/recall.mdx:195-212`). `exact` is the one mode that is not simply "at least/all of these tags plus maybe more" — it requires the memory's *complete* tag set to equal the requested set, and excludes untagged memories, **except** that with tags omitted/`null`/`[]` it selects the untagged/global scope rather than matching nothing (`api/recall.mdx:209`). For every other mode, an omitted/`null`/empty tags list is treated as "no filter" (all tagged and untagged memories match) — this is the trap HS-07 already flagged, confirmed unchanged. `tags_match: "exact"` governs *recall-time filtering*, not retain-time consolidation — see HS-08 for the separate `observation_scopes` setting that governs how observations are synthesised, which `tags_match` cannot retroactively fix.

**Replace semantics.** `MemoryItem.update_mode` (OpenAPI): `"replace"` (the default) "deletes old data and reprocesses from scratch"; `"append"` "concatenates new content to the existing document text and reprocesses" (`api/retain.mdx:116-145` describes the same behavior in prose). `RetainRequest.operation_id` (OpenAPI) is a client-supplied UUID that is the identity of an *async* retain operation: re-submitting the same `operation_id` returns the original operation and enqueues no new work (safe retry after a lost/timed-out acknowledgement); reusing an id that belongs to a different operation returns `409`; it is ignored for synchronous retain. Qualifying the original claim: there is still no ETag/revision/If-Match concurrency control on the document resource itself, so Métis's own revision/fencing layer (HS-10) remains necessary for out-of-order retries and concurrent-ACL-change safety — but async retain retries *can* now be made idempotent via `operation_id`, which the original note did not have. Tag replacement has its own footgun worth carrying forward even though it wasn't in the original 18: `PATCH /v1/default/banks/{bank_id}/documents/{document_id}` with body `{"tags": [...]}` **replaces** the whole tag array rather than merging (`api/documents.mdx:124`) — omitting the field is rejected with `422`, but sending an incomplete array silently drops tags.

**One packaging note found in passing, not in the original 18 or in the SOURCES.json register:** the OpenAPI copy vendored into `skills/hindsight-docs/references/openapi.json` still reads `"version": "0.10.0"` at the `v0.10.1` release commit — it lagged one release at the moment `v0.10.1` was cut. The two files are otherwise byte-identical: both are 570,730 bytes, and `cmp -l` against `hindsight-docs/static/openapi.json` reports exactly one differing byte, offset 307 (0-indexed), `0` vs `1` — the last digit of `info.version`. **Use `hindsight-docs/static/openapi.json` as the canonical schema source, not the skills-embedded copy**, if either is ever vendored into Métis's own repo.
